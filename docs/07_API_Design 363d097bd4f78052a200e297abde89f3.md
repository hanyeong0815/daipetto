# **2-7. 日時形式**

```
2026-05-17T10:00:00+09:00
```

ISO-8601形式を利用する。

応答の日時（`createdAt`など）は**JSTのオフセット付き・秒単位**で返す（例: `2026-05-17T10:00:00+09:00`、`LocalDateTimeJsonSerializer`）。日付のみの項目（`recordedDate`・`scheduledDate`など）は`2026-05-17`、時刻のみの項目（`startTime`など）は`10:00:00`の形式で、オフセットを付けない（どちらもJSTの日付・時刻として扱う）。

基準タイムゾーンは**JST（Asia/Tokyo、UTC+9）**とする（日本向けサービスのため）。Spring APIは起動時にJVMの既定タイムゾーンをJSTに固定し、実行環境（UTCのコンテナ等）に依存しない。`recordedDate`省略時の「当日」や過去日時の判定もJSTで行う。フロントエンドも「今日」をJSTで計算する。

# **2-8. 病院管理者の所属チェック**

`ROLE_HOSPITAL_ADMIN`は`hospital_admins`（`06_ERD` §11）で紐付いた病院だけを管理できる。`ROLE_SYSTEM_ADMIN`はすべての病院を管理できる。紐付いていない病院を操作すると**403 HOSPITAL-005**。

| **対象API** | **確認する病院** |
| --- | --- |
| 8-4〜8-7・8-9〜8-11（予約枠・営業時間の管理、予約枠の自動生成）、11-2 病院更新 | パスの`hospitalId` |
| 9-5〜9-7（予約の承認・却下・診療完了） | 予約の病院（予約が存在しなければ先にRESERVATION-006） |
| 9-8 予約一覧（病院管理者） | Queryの`hospitalId` |

- 所属は他の検証より先に確認する。病院管理者が紐付いていない`hospitalId`（存在しない病院を含む）を指定すると、HOSPITAL-001〜003ではなくHOSPITAL-005になる。
- 権限・紐付けはリクエストごとにDBの現在の値で判定する（`09_Security_Design` §4-5）。紐付けを解除された病院管理者は、次のリクエストから操作できない。
- 紐付けの管理（11-9〜11-11）と病院の登録・停止（11-1・11-3）は`ROLE_SYSTEM_ADMIN`のみ。

# **3-3. ログアウト**

## **Endpoint**

```
POST /api/v1/auth/logout
```

---

## **説明**

ログイン中のユーザー（`Authorization: Bearer <Access Token>`）の**有効なRefresh Tokenをすべて失効**させる。ログイン・再発行と同じユーザー行の排他を取ってから一括失効し、同時に進行中の再発行が発行した後続Tokenも残さない（`09_Security_Design` §3-5）。Request本文は不要（送られても使わない）。

---

## **Response**

```json
{
  "success": true,
  "data": {
    "isLogout": true
  },
  "message": "ログアウトしました。"
}
```

---

## **異常系**

| **Code** | **内容** |
| --- | --- |
| AUTH-001 | 未認証（Access Tokenなし・無効） |

> **注記（2026-10-23 単体テストで修正）:** 以前は「Request本文の`refreshToken`を失効させ、`data: null`を返す」と記載していたが、2026-09のセッション直列化（`09_Security_Design` §3-5）で実装はユーザー単位の一括失効に変わっていた。実装に合わせて記述を更新した（`test/` UT-01-013）。

# **6-3. 健康記録更新**

## **Endpoint**

```
PATCH /api/v1/health-records/{healthRecordId}
```

---

## **説明**

部分更新を行う。**null（未指定）の項目は既存値を維持する**（空のPATCHは何も変更しない）。`symptom`・`memo`は空文字を指定すると消去（NULL）される。`weight`はPATCHでは消去できない。更新は対象の記録を行ロック付きで読み取り（`SELECT … FOR NO KEY UPDATE`）、同じトランザクション内で内容列だけを`deleted_at IS NULL`の行に限って書き込む。同じ記録への別のPATCHや論理削除とは直列化されるため、未指定項目は**その時点で確定している最新値**を維持する（別のPATCHが変更した項目を古い値で戻さない）。同じ項目を同時に変更した場合は後に確定した方が残る。論理削除が先に確定した場合はHEALTH-001となり、削除が最終状態として維持される。本プロジェクトは部分更新をPATCHで統一しているため、当初PUTで記載していたものをPATCHに変更した（§11-2 病院更新と同じ理由）。

---

## **異常系**

| **Code** | **内容** |
| --- | --- |
| HEALTH-001 | 存在しない健康記録 |
| HEALTH-002 | 対象ペットが他ユーザーのもの |
| VALIDATION-001 | `weight`が負数、または桁数超過 |

# **6-5. ワクチン接種予定API**

ワクチン接種予定（`vaccinations`）も`pet_id`のみを持つため、所有者判定は健康記録と同じく対象ペット経由で行う（他ユーザーのペットはVACCINATION-002）。状態は`SCHEDULED`/`COMPLETED`/`CANCELLED`（`08_State_Design` §7）。状態遷移は遷移元の状態を`WHERE`条件にした列単位のUPDATEで書き込み、同時に別の遷移が先に確定していた場合は0件更新となりVACCINATION-003を返す。

| **API** | **遷移** | **状態** |
| --- | --- | --- |
| 6-6 一覧取得 | — | 実装済 |
| 6-7 登録 | → SCHEDULED | 実装済 |
| 6-8 接種完了 | SCHEDULED → COMPLETED | 実装済 |
| 6-9 中止 | SCHEDULED → CANCELLED | 実装済 |
| 6-10 再登録 | CANCELLED → SCHEDULED | 実装済 |
| 6-11 削除 | 論理削除 | 実装済 |

```
Spring   → FastAPI GET /internal/v1/analysis/pets/{petId}/...（X-Internal-Api-Key）
```

## **共通ルール**

| **項目** | **内容** |
| --- | --- |
| 対象データ | 指定ペットの、論理削除されていない健康記録（`health_records`）・ワクチン接種予定（`vaccinations`） |
| 権限 | ペットの飼い主本人のみ（健康記録APIと同じ） |
| 期間指定 | `from`・`to`（`YYYY-MM-DD`、どちらも任意・両端を含む、記録日 `recorded_date` 基準）。省略した側は制限なし |

# **7-2. 健康スコア取得**

## **Endpoint**

```
GET /api/v1/analysis/pets/{petId}/health-score
```

---

## **説明**

直近30日（今日を含む30日間）の健康記録から、体重変化と症状の頻度で 0〜100 の参考スコアを算出する。診断ではなく、画面では「参考値」として表示する。

| **要素（type）** | **評価方法** | **減点** |
| --- | --- | --- |
| WEIGHT_CHANGE | 期間内の日別体重が2件以上ある場合に、最初と最後の変化率の絶対値（%）を評価。1件以下なら評価しない（`evaluated: false`、減点0） | 10%以上: 30、5%以上10%未満: 15、5%未満: 0 |
| SYMPTOM_FREQUENCY | 症状が入力された記録がある日数を数える（同じ日の複数記録は1日） | 1日につき10（最大40） |

`score` = 100 − 減点の合計。`grade` は 80以上 `GOOD`、50〜79 `CAUTION`、49以下 `WARNING`。期間内に健康記録が1件も無い場合は `score: null`、`grade: "NO_DATA"`。`value` は WEIGHT_CHANGE が変化率の絶対値（%、小数1桁の数値）、SYMPTOM_FREQUENCY が日数（整数）。評価しない場合は `null`。体重の減点の境界は、表示する小数1桁の値で判定する（例: 4.95% は 5.0% として15点減点）。最初の体重が0のときは WEIGHT_CHANGE を評価しない。症状は、前後の空白を除いて空でないものを「入力あり」とする。

```json

  "data": {
    "score": 75,
    "grade": "CAUTION",
    "period": { "from": "2026-09-26", "to": "2026-10-25" },
    "factors": [
      { "type": "WEIGHT_CHANGE", "evaluated": true, "penalty": 15, "value": 6.2 },
```

# **8-11. 予約枠の自動生成（手動実行）**

## **Endpoint**

```
POST /api/v1/admin/hospitals/{hospitalId}/schedules/generate
```

## **説明**

曜日別営業時間（8-7）を元に、指定した月の予約枠を生成する（`06_ERD` §18の生成ロジック）。毎月1日のScheduler（翌月分、`04_System_Architecture` §14）と同じ処理を、管理画面から任意の月に対して実行する。

- 営業開始〜休憩開始・休憩終了〜営業終了を予約枠単位で区切って`AVAILABLE`、休憩時間も同じ単位で区切って`BLOCKED`の枠を作る。区間の端数（単位に満たない残り）は作らない。
- 営業時間の無い曜日は作らない（休診）。
- **既に予約枠が1つでもある日は作らない**（手動の枠や臨時の`BLOCKED`を上書きしないため）。同じ月を再実行しても枠は増えない。
- 指定できるのは今月〜12か月先（JST）。今月を指定した場合は今日以降の日だけを作る。
- 同じ病院の生成は病院行の排他（`SELECT ... FOR UPDATE`）で直列化し、同時に実行しても同じ日に枠が二重にできない。
- 停止中（`SUSPENDED`）の病院も生成できる（Schedulerは営業中の病院だけが対象）。

## **権限**

| **Role** |
| --- |
| ROLE_HOSPITAL_ADMIN（紐付いた病院のみ、§2-8） |
| ROLE_SYSTEM_ADMIN |

## **Request**

```json
{
  "month": "2026-11"
}
```

## **Response**

```json
{
  "success": true,
  "data": {
    "createdSlots": 120,
    "generatedDates": 20,
    "skippedDates": 1
```

# **10. 通知API**

通知を作成する公開APIは提供しない。通知はシステムが生成する:

| 生成契機 | 種別 | 状態 |
| --- | --- | --- |
| 予約承認（§9-5） | RESERVATION_APPROVED | 実装済 |
| 予約却下（§9-6） | RESERVATION_REJECTED | 実装済 |
| 診療完了（§9-7） | TREATMENT_COMPLETED | 実装済 |
| ワクチン接種リマインダー（毎日09:00 JSTのScheduler、`08_State_Design` §11） | VACCINATION | 実装済 |

予約の状態変更と通知生成は同一トランザクションで行う（`08_State_Design` §6-6）。状態遷移が成立しなかった場合は通知を作成しない。予約キャンセルは §6-6 に通知定義が無いため通知を生成しない。

ワクチン接種リマインダーは、接種予定日が当日〜7日後の`SCHEDULED`の予定について飼い主へ1件ずつ生成する。本文は「{ペット名}の{ワクチン名}接種予定日（{予定日}）が近づいています。」。通知は予定日ごとに1回だけ生成する（重複防止）。送信時に`reminded_date`へその予定日を条件付きUPDATEで書き込み、書き込めた場合だけ通知を作る。抽出後に中止・再登録・完了・削除が確定していれば書き込めないため、古い予定日の通知は作らない。論理削除されたペット・予定は対象外。
